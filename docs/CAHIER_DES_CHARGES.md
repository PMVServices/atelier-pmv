# Cahier des charges — Atelier PMV

Ce document fixe ce qui est **en place et validé**. Toute modification doit le respecter ; si une demande le contredit,
on le dit avant de coder et on met ce document à jour une fois la décision prise.
Aucun code d'accès ni clé n'est écrit ici (ils sont saisis par l'utilisateur dans l'application).

## 1. Contexte

- Application interne de PMV Services (Thibaud Perroche) : fiches d'entretien atelier et chantier, planning, matériel à commander, stock.
- React (Create React App) + Supabase (clé anonyme, pas de DDL côté appli : le SQL est collé par l'utilisateur).
- Déploiement : chaque push sur `main` de `PMVServices/atelier-pmv` déclenche Vercel → https://atelier-pmv.vercel.app (PWA).
- Appareils : **iPhone / iPad (usage principal sur le terrain)**, tablette d'atelier partagée, PC.
- Langue : français partout. Réponses courtes, vocabulaire de l'atelier.

## 2. Règles de collaboration

1. Périmètre serré : ne modifier que ce qui est demandé.
2. Ne jamais toucher, supprimer ni « nettoyer » des données réelles sans demande explicite.
3. Tester dans un vrai navigateur avant chaque push (build `CI=true npm run build` : les avertissements sont des erreurs).
4. Ne jamais demander ni saisir de mot de passe, clé ou identifiant à la place de l'utilisateur.
5. En cas d'ambiguïté : poser la question avant de coder.
6. **Ce qui existe ne change pas sans accord** : une nouvelle fonction ne doit pas modifier l'affichage ou le comportement des autres.

## 3. Affichage — contraintes impératives

Un téléphone qui affiche la page dézoomée ou décalée = régression majeure (déjà arrivée : bouton « Admin » ajouté dans l'en-tête).

- **Aucun débordement horizontal** à 320, 360, 390, 768, 900, 1000, 1280, 1366, 1440 et 1800 px de large, dans les deux rôles (technicien et administrateur), avec et sans technicien choisi.
  Sur iPhone, un seul élément trop large dézoome toute la page.
- **Ordinateur : pleine largeur (demande du 21/10/2026)** : à partir de **1000 px** de large, les pages n'ont plus de largeur maximale (avant : 700 à 1200 px, centrées). Mécanisme : les conteneurs de page déclarent `maxWidth:"var(--lp, <largeur d'origine>)"` et `public/index.html` définit `--lp: none` à partir de 1000 px (idem pour `.mat` et `.stk` dans leurs feuilles de style) ; **tout nouveau conteneur de page doit suivre cette règle**. Pour que le contenu reste lisible : **fiches atelier et chantier** : les champs se rangent dans une **grille de cases toutes de même largeur : 2 colonnes (4 à partir de 1500 px)**, lue de gauche à droite puis de haut en bas dans l'ordre de la fiche (demandes du 21/10/2026 : « ça fait fouilli », « la trame n'est pas agréable et instinctive »). Un groupe de champs liés (isolement + DAR, flasque + arbre…) reste sur une même ligne : s'il ne tient pas dans ce qui reste de la ligne il passe à la suivante ; un champ dont le voisin du groupe est masqué n'occupe qu'une case ; les champs larges (textes longs, techniciens, contact, joints, matériel, photos, intertitres, messages) prennent toute la ligne, plafonnés à 1000 px (sauf intertitres et photos). **Intertitres automatiques** (≥ 1000 px seulement) : `INTERTITRES_TRAME` dans `App.js` place un intertitre et une nouvelle ligne avant certains champs (ex. « Côté avant : roulement, flasque, arbre, joints », « Joint de corps », « Garniture mécanique », « Intensités », « Vibrations », « Mesure ADX »…), pour les fiches moteur, pompe, moto-réducteur, « Autre matériel » ; ajouter une ligne `id_du_champ:"Titre"` à cette table suffit (code : `trameFiche`, `RenduChamps`, `rendreChamps`). **Liste des fiches atelier** : colonnes Type, Statut et Entrée en plus (≥ 1100 px). **Tableau de bord** : les blocs de notifications sur deux colonnes (≥ 1100 px). **Listes de cartes** (clients, dossiers atelier et chantier, rapports) : classe `grille-large` = plusieurs colonnes de 460 px minimum. **Stock** : gros boutons et chips plafonnés, liste d'articles sur plusieurs colonnes. Sous 1000 px rien ne change.
- En-tête : barre d'onglets complète seulement à partir de **1400 px** ; en dessous, menu ☰. Chaque nouvel onglet élargit la barre : après en avoir ajouté un, remesurer le pire cas (administrateur au nom très long) et ajuster ce seuil (`isMobile` et le décalage de l'en-tête de fiche chantier dans `App.js`).
  La pastille de la personne connectée est dans l'en-tête (ordinateur), la ligne « personne » en haut du menu ☰ (téléphone / tablette) ; l'en-tête de `/stock/` n'a que l'icône.
  Le badge de stockage se compacte sous 380 px (« Gérer » masqué) puis 340 px (barre masquée).
  Le nom du technicien dans l'en-tête est tronqué (110 px max) avec le nom complet en info-bulle.
- Une règle globale `@media (pointer: coarse)` agrandit boutons et champs (≈ 44-47 px) sur écran tactile : en tenir compte pour tout élément placé dans l'en-tête ou dans une ligne serrée.
- Fiche chantier/atelier : champs courts rangés par deux seulement à partir de 600 px (`grilleCols`, `useWidth`) ; une colonne en dessous.
  Colonnes de cartes : 1 colonne < 600 px, 2 colonnes de 600 à 899 px, le nombre prévu au-delà.
- **Tableau de bord** : sur téléphone (moins de 600 px) seuls le bouton « Matériel à commander » et les raccourcis s'affichent ; les notifications (matériel, fiches urgentes, à faire rapidement, devis en attente, commandes, fiches à exporter) s'affichent sur tablette et ordinateur. Dans « Fiches terminées à exporter », chaque fiche a un bouton « Déjà fait » qui la retire de la liste sans télécharger (même marqueur que l'export).
- Pas de texte coupé sans solution (retour à la ligne, défilement dans son propre bloc ou points de suspension).

### Contrôle avant chaque livraison (obligatoire pour toute modification visible)

1. `CI=true npm run build` sans erreur.
2. Lancer l'appli, ouvrir les pages touchées **et** le tableau de bord, la liste Atelier, la liste Chantier, Matériel, Stock.
3. Pour chaque largeur de la liste ci-dessus (fenêtre redimensionnée **puis page rechargée**), en administrateur et en technicien :
   `document.documentElement.scrollWidth <= window.innerWidth` et, pour l'en-tête, `scrollWidth <= largeur affichée`.
   Mesure type (console du navigateur) :

   ```js
   const W=innerWidth;
   const e=[...document.querySelectorAll("div")].find(d=>d.style.position==="sticky"&&d.style.top==="0px"&&d.querySelector("img"));
   ({W,pageDebordante:document.documentElement.scrollWidth>W,entete:e.getBoundingClientRect().width+" / "+e.scrollWidth})
   ```
4. Cas le plus chargé de l'en-tête (PC) : administrateur + technicien choisi avec un long nom, au seuil de la barre complète (1400 px) et un pixel en dessous.
5. Remettre le navigateur de test dans son état initial (rôle, brouillon, taille de fenêtre) et ne laisser aucune donnée de test dans la base.

## 4. Accès et rôles

- **Code de l'appareil** (`PIN_CODE` dans `App.js`) : demandé **une seule fois par appareil**, puis mémorisé (`pmv_pin_ok`) ; ensuite l'appli demande seulement qui ouvre.
- **« Qui ouvre l'application ? »** à chaque ouverture : tous les noms (Nom Prénom) visibles d'un coup en boutons larges (grille, sans défilement interne tant que la liste tient à l'écran, recherche au-delà de 24 personnes), bouton « Continuer : <dernière personne> » en tête. Le **profil de la personne** choisie décide de ce qu'elle voit : Administrateur, Technicien ou Commercial. Le choix est gardé pour la session (un rechargement ne redemande pas), la fermeture de l'appli le redemande.
- **Changer de personne** : pastille de la personne dans l'en-tête (ordinateur) ou ligne en haut du menu ☰ (téléphone / tablette) → fenêtre « Changer de personne » ; l'administrateur y trouve aussi « Gérer les accès ». Même mécanisme dans l'écran /stock/.
- **Liste des personnes** : base `parametres_app`, clé `acces_personnes` (JSON : id, nom, prénom, profil, initiales). Gérée dans l'écran « Accès » (administrateur) : ajout un par un ou par lot (« Nom Prénom » par ligne), changement de profil, initiales (celles des techniciens existants, pour préremplir « qui a fait la fiche »), retrait ; au moins un administrateur doit rester, on ne peut pas se retirer soi-même.
- **Première utilisation** (aucune personne enregistrée) : écran qui demande le code administrateur historique (une seule fois, constante `ADMIN_CODE` de `App.js`) puis le nom et le prénom du premier administrateur.
- Une personne qui a des initiales n'a plus à les donner à chaque nouvelle fiche ; l'ancienne pastille « initiales du technicien » de l'en-tête a disparu.
- **Limite à rappeler** : le code de l'appareil protège l'entrée, mais il est commun et visible dans le code du site ; ensuite l'accès repose sur le choix du nom. Barrière d'interface uniquement, la base reste accessible avec la clé publique de l'appli. Le dépôt GitHub est public.

## 5. Fiche Atelier

- Types de matériel et étapes existants ; photos, aperçu, export PDF + ZIP, duplication, dossiers client → N° DE → lieu.
- N° DE toujours au format « DE0000 » (des chiffres seuls reçoivent le préfixe DE) ; **« DV0000 » pour les clients de PMV Rail** (voir § 6 sexies : le préfixe suit le client, partout).
- **En-tête de la fiche atelier épinglé** (demande du 21/10/2026, PC, tablette et téléphone) : le bandeau bleu (N° DE · client · matériel, statut, avancement, boutons) reste visible en haut quand on défile, **juste sous la barre de l'appli** : son décalage est mesuré sur la barre réelle (`id="entete-app"` dans `App.js` ; 52 px sous 1400 px de large, 56 au-delà ; auparavant fixé à 56 px, d'où 4 px de vide sous 1400 px). Sous 600 px (téléphone) il est compact : une ligne de titre + une ligne de boutons, sans le chemin du dossier ni la barre d'avancement (le % reste, sauf sous 360 px) ; sur écran tactile ses boutons font 36 px au lieu de 44 (règle `.entete-fiche` dans `public/index.html`). Boutons : **👁** aperçu, **💾 Enregistrer** (à la place de l'ancien « ⬇ » qui téléchargeait / partageait le fichier : le téléchargement reste en bas de la fiche, avec « Imprimer / PDF »), **📄** imprimer / PDF, **← Retour**. Le bouton 💾 enregistre toutes les valeurs et les commentaires **sans valider d'étape ni quitter** (comme « Enregistrer et quitter ») ; il est **orange** quand il y a des modifications non enregistrées (ou fiche pas encore créée), **⏳** pendant l'enregistrement, **✅ vert** une fois fait, **⚠ rouge** en cas d'échec (le message détaillé est en haut de la fiche).
- **Mesure ADX en « Infos électriques » — choix « Non fait »** (demande du 21/10/2026, toutes les fiches atelier : moteur, « Autre matériel », pompe, moto-réducteur, ventilateur, y compris le 2e passage des infos électriques du moteur ; pas la cheminée, dont l'ADX6 est une capture) : les listes « ADX mesure isol. … — résultat » (sans / avec variateur 2800 V / sans variateur 2000 V) proposent **PASS · Douteux · Hors Tolérance · Non fait**. Avec « Non fait », la case « … — valeur » correspondante **disparaît** (et n'est plus obligatoire, ni imprimée dans la fiche PDF). Technique : nouvelle forme de condition `{champ, sauf}` (= « différent de », vrai tant que la question n'est pas répondue), seule ou dans une liste de conditions (toutes vraies), lue par `champVisible` (`App.js`) et `champVisiblePdf` (`pdfUtils.js`) ; `suffixerChamps` la reprend pour le 2e passage. Effet de bord : le PDF/l'aperçu respectent maintenant aussi les conditions en liste (ex. « Vérif rotor court-circuit — résultat »), comme à l'écran.
- **Une fiche atelier n’est modifiée que par une personne à la fois (verrou, demande du 21/10/2026)** : quand quelqu’un ouvre une fiche existante, elle est verrouillée à son nom ; une autre personne (autre tablette, téléphone ou PC) qui l’ouvre arrive sur un écran « 🔒 Fiche en cours de modification par … depuis HH:MM » et peut seulement **la voir en lecture seule** (bouton « 👁 Voir la fiche »), « 🔄 Réessayer » ou revenir à la liste. Dans la liste des fiches (vues Fiches et Dossiers), la fiche porte un badge **« 🔒 nom »** (mis à jour toutes les 20 s) ; on peut quand même l’ouvrir, en lecture seule. Le verrou se libère quand la personne **quitte la fiche** (bouton ← Retour, fermeture de l’appli) ou **5 minutes sans activité** (tablette éteinte, appli fermée de force) ; la fiche ouverte renouvelle son signe de vie toutes les 30 s. Si la fiche se libère pendant qu’on la regarde (ou si l’avancement a changé depuis l’ouverture de la liste), elle est **rouverte à jour** avant toute saisie (le brouillon local est abandonné) pour ne jamais écraser le travail de l’autre. **Supprimer** une fiche tenue par quelqu’un d’autre est refusé. Un verrou laissé par **le même appareil** (page rechargée) est repris tout de suite. **Hors connexion ou erreur réseau : on ne bloque jamais le travail** (la fiche s’ouvre normalement, sans protection). Technique : `src/verrouFiche.js` ; aucune table à créer : une ligne par fiche dans `parametres_app` (clé `verrou_fiche_<id>`, valeur JSON {p personne, d appareil, s session, a heure de prise, t dernier signe de vie}) ; prise atomique (insertion sans écraser, reprise par remplacement conditionnel) ; libération = ligne marquée périmée (`t` = 0) puis supprimée si la base l’autorise. **L'administrateur n'est jamais mis en lecture seule** (demande du 21/10/2026) : il ouvre toujours la fiche en modification et **reprend le verrou** ; la personne qui l'avait voit alors « Fiche reprise par … — vos modifications non enregistrées n'ont pas été prises en compte » à son prochain signe de vie (30 s au plus). Hors périmètre : fiche chantier, cartes du planning, page du rapport client. Ouvrir la fiche avec le bouton 👁 de la liste la verrouille aussi tant qu’on est sur la page de la fiche.
- Une fiche peut être préremplie depuis une fiche chantier (case « Entretien en atelier »).
- **Technicien de chaque étape** (fiche atelier) : la personne qui a ouvert l'appli (si elle a des initiales) est cochée d'office quand le champ est vide. Si on **décoche son nom**, l'appli demande « Qui utilise l'application ? » (fenêtre par-dessus la fiche, qui reste ouverte) : la personne choisie devient celle qui a ouvert (en-tête) et se coche à la place ; « Annuler » remet le coche. Cocher un deuxième technicien ne pose aucune question. La fiche chantier garde son propre champ technicien.
- Le bouton « Ajouter photo » de la liste atelier fonctionne (upload via `db.uploadPhoto`).
- Types proposés au choix « Nouvelle fiche » : Moteur, Pompe, Moto-réducteur, **Ventilateur** (voir ci-dessous), **Autre matériel** (il remplace les anciennes cartes « Bientôt disponible » Ventilation et Réducteur, qui n'étaient pas utilisables).
  « Autre matériel » (`type_materiel` = « Autre ») suit exactement le déroulement du moteur (mêmes étapes, devis, rapport) ; seul s'ajoute le champ obligatoire « Type de matériel » (ventilateur, treuil, compresseur…) saisi à la main, juste avant « Matériel / Identification lieux ». Il apparaît dans l'en-tête, l'aperçu et le PDF.
- **Fiche Ventilateur** (`type_materiel` = « Ventilateur », champs et étapes dans `App.js` : `CHAMPS_VENTILATEUR`, `etapesVentilateurPour`) :
  - **Entrée** (comme la pompe) + 3 décisions qui pilotent la suite : **type** (centrifuge — turbine / roue à aubes, hélicoïde, hélico-centrifuge, tangentiel, moto-turbine, VMC, soufflante, surpresseur, autre avec texte libre), **ce qui est reçu** (moteur + ventilateur, ou ventilateur seul ; un moteur reçu seul se traite avec la fiche Moteur) et **entraînement** (direct, poulies et courroies, accouplement, moteur intégré, autre). Plaque et identité du moteur demandées seulement si le moteur est reçu.
  - Étapes : Entrée → **Description du ventilateur** → Infos électriques → Rotation avant démontage moteur → Rotation avant démontage ventilateur → Matériel au démontage moteur → **Ventilateur au démontage** → (Suivi devis et commande si devis nécessaire) → Essais après remontage. **Ventilateur seul** : toutes les étapes du moteur disparaissent. **Moteur neuf** (première question de « Infos électriques », comme le moteur seul) : « Rotation avant démontage moteur » et « Matériel au démontage moteur » sont sautées ; les étapes du ventilateur restent.
  - **Description** : marque (liste + autre), plaque (type / modèle, n° de série, vitesse, puissance avec unité, débit, pression — tous facultatifs), sens de rotation (obligatoire), puis selon le type : turbine (diamètre, hauteur, taille d'arbre, matière, nombre et forme des aubes, orientation de la sortie), hélice (nombre et longueur des pales, diamètre, pas, alésage du moyeu, matière), rotor tangentiel (longueur, diamètre, pales, matière, axe) ; grille (oui / non, diamètre), entraxe de fixation, montage (dont « sur plaque avec le moteur »), caisson (oui / non, longueur × largeur × hauteur) et un champ texte libre. Les listes proposent presque toujours « Autre » avec texte libre.
  - **Ventilateur au démontage** : « ventilateur neuf » (Oui / Non / Ne sais pas encore, « Oui » masque le démontage et demande la marque, le modèle, le n° de série et les dimensions du neuf) ; sinon état de la roue / hélice / rotor, nettoyage, équilibrage nécessaire, roue à remplacer, jeu hélice / virole, fixation de la roue, arbre et clavette ; **paliers propres** (roulements et joints de chaque côté) ; **poulies et courroies** (diamètres, états, profil, nombre, entraxe) si l'entraînement en comporte ; **accouplement** si l'entraînement en comporte ; carter / volute, silentblocs, grille, caisson, peinture, autres pièces, travaux conseillés.
  - **Essais après remontage** : mesures du moteur (si reçu), sens de rotation, bruit, vibrations des paliers du ventilateur, « équilibrage réalisé » (oui / non seulement : aucune norme ni valeur de balourd demandée), débit mesuré, travaux effectués, contrôle qualité.
  - Pièces à commander détectées automatiquement (roue, roulements, courroies, poulies, accouplement, silentblocs, joints) ; **rapport client** : le bouton « 📧 Rapport client » existe, mais le contenu du rapport (pompe, ventilateur) se compose entièrement dans Maintenance → Rapports (§ 10 ter).
  - Aperçu, PDF et exports ZIP : le type de la fiche (`_type`) est maintenant transmis aux exports faits depuis les listes, pour que toutes les fiches (pompe, moto-réducteur, ventilateur) utilisent leurs propres champs.
- **Étape « non réalisable »** (fiche atelier, toutes les étapes sauf la première) : la case ouvre une **justification obligatoire** (dictée possible) ; sans elle on ne peut pas valider l'étape. L'état et la justification sont **enregistrés avec la fiche** (valeurs `nr_<étape>` = Oui/Non et `nrj_<étape>`, clés tirées du nom de l'étape, module `src/etapeNr.js`) : avant, l'état se perdait au rechargement et n'apparaissait ni dans l'aperçu téléchargé ni dans l'impression. **Aperçu, PDF, impression, export HTML / ZIP** : l'étape garde son titre (et le technicien), puis une ligne « ⚠ Non réalisable » et la ligne « Justification » ; ses champs et ses photos n'apparaissent pas. Dans la liste des étapes validées, le résumé affiche « Non réalisable — <justification> ».
- **Onglet « Fiche Atelier » : deux sous-onglets** (`PageAccueil`, dernier choix mémorisé sur l'appareil, `pmv_atelier_sous`) : **« 📋 Fiches (n) »** = une ligne par fiche avec seulement N° DE, client et matériel (tableau à partir de 700 px, cartes en dessous) ; un clic sur la ligne ouvre la fiche, le bouton **« 📁 Dossier »** de la ligne bascule vers le sous-onglet Dossiers avec le client et le N° DE déjà ouverts ; **« 📁 Dossiers (n) »** = l'arborescence habituelle client > N° DE > fiche, où chaque dossier N° DE qui ne contient qu'une fiche a un lien direct **« 📄 Fiche »** qui ouvre la fiche sans déplier. La recherche et le filtre de statut s'appliquent aux deux sous-onglets.
- **Modifier une étape déjà validée** (fiche atelier) : on ouvre l'étape dans la liste (▼) ; elle propose la case « non réalisable » (avec sa justification obligatoire, sauf étape 1) et un bouton **« 💾 Enregistrer cette étape »** (désactivé tant que des champs obligatoires manquent ou que la justification est vide) qui enregistre toute la fiche, supprime les valeurs vidées et ajoute « Étape modifiée » à l'historique. Une étape validée « non réalisable » est signalée par ⚠️ et « · non réalisable » dans son en-tête. L'enregistrement n'invalide pas les étapes suivantes et ne change pas le statut (une fiche « Terminée » le reste ; l'ancien « Enregistrer » la repassait « En cours »).
- **Bouton « ← Retour » et modifications non enregistrées** (fiche atelier, en-tête et bas de page) : la fiche compare ses valeurs et ses commentaires au dernier état enregistré (pris 1,2 s après l'ouverture, pour ignorer les préremplissages automatiques). S'il y a des modifications, une fenêtre propose **« Enregistrer et quitter »**, **« Quitter sans enregistrer »** ou **« Annuler, rester sur la fiche »** ; sans modification, on part tout de suite. Le navigateur prévient aussi à la fermeture de l'onglet tant que des modifications ne sont pas enregistrées. Les photos, enregistrées dès l'envoi, ne comptent pas comme modification.
- **Export HTML / ZIP d'une fiche atelier** (liste atelier « ZIP + PDF » et export du tableau de bord) : même contenu que l'aperçu (valeurs, statut, commentaires, pièces à commander, étapes selon le type) via `chargerPourExport`. Corrigé : la requête triait `fiche_valeurs` sur `created_at`, colonne qui n'existe pas (c'est `updated_at`) ; la base répondait par une erreur et le fichier HTML sortait avec toutes les cases vides (seuls N° DE, client et lieu, repris de la liste, étaient remplis). Ne jamais trier `fiche_valeurs` sur `created_at`.
- **Entrée** (moteur, pompe, moto-réducteur, autre matériel) : obligatoires — marque moteur, puissance, vitesse, type, numéro de série, fixation et contact. Case « Rapport client demandé ? » (Oui/Non, obligatoire) après « Devis / bon de commande nécessaire ». Délai demandé : l'unité propose « Pas de délai demandé » (la durée disparaît alors, aucune échéance n'est calculée).
- **Conseil « petit moteur »** (moteur et « Autre matériel ») : à la fin de l'Entrée, si la puissance saisie est de **4 kW ou moins** (conversion automatique des W, CV, HP, et kVA × 0,8), un encadré rappelle de proposer au client un moteur neuf plutôt que l'entretien si le moteur est « basique ». Simple conseil, jamais bloquant, absent de l'aperçu et du PDF.
- **Cases libres** (toutes les fiches atelier, chaque étape) : bouton « ➕ Ajouter une case libre » → on donne un nom (une marque, une particularité…) puis on remplit un champ de texte libre (dictée possible) ; plusieurs par étape, retirables. Rangées dans le champ `cases_libres` (JSON). Elles figurent dans l'aperçu, le PDF et les exports de la fiche, dans l'étape où elles ont été ajoutées, **seulement si elles ont une valeur** ; elles ne sont **pas** reprises dans le rapport client. Non disponibles dans la fiche chantier.
- **Moteur neuf** : les trois choix sont Oui / Non / **Ne sais pas encore** ; « Ne sais pas encore » se comporte comme « Non » partout. Pour le moteur seul et « Autre matériel », la question est posée en premier dans « Infos électriques » (`moteur_neuf_debut`) ; avec « Oui », seuls le technicien reste à renseigner et **une question « Essais du moteur neuf ? » (Oui / Non, obligatoire, `essais_moteur_neuf`)** est posée : « Non » = la fiche s'arrête après cette étape (statut « Terminée », le statut chantier n'est pas modifié) ; **« Oui » = la fiche continue avec l'étape « Information des essais après remontage »**, exactement la même que d'habitude (décision du 20/10/2026 ; moteur seul et « Autre matériel » seulement, pas la pompe ni le ventilateur). Pompe et moto-réducteur : la question existante (étape « Matériel au démontage moteur ») gagne seulement l'option « Ne sais pas encore ».
- **DAR enroulements** : une 2e mesure (DAR) est rangée à côté de « Isolement enroulements — plus petite valeur » dans les étapes de rotation avant démontage (moteur, pompe, moto-réducteur).
- **Photos** (fiches atelier et chantier, listes atelier et chantier) : on peut glisser-déposer une ou plusieurs photos sur le bloc d'ajout après avoir choisi la catégorie (sur ordinateur) ; chaque vignette a une petite croix ✕ (avec confirmation) qui supprime la ligne en base puis le fichier s'il n'est plus utilisé. Le numéro d'une nouvelle photo ne reprend jamais un nom existant. La croix n'est pas un `<button>` : sur tablette les boutons sont agrandis.
- **Ajout de photo : quatre façons, partout** (composant `SourcesPhoto`, `src/Photos.js`) : « 📁 Choisir un fichier », « 📷 Prendre une photo » (appareil photo de la tablette / du téléphone), glisser-déposer (ordinateur) et « 📋 Coller » (bouton, ou Ctrl+V : va à la dernière zone survolée ou cliquée, ignoré dans un champ de texte). Utilisé par les photos obligatoires, les photos d'étape, les listes atelier et chantier, les photos du rapport et ses captures d'appareil. Un nouvel endroit d'ajout de photo doit réutiliser ce composant.
- **Photos de chantier** : la table `fiches_chantier_photos` n'a pas les colonnes `etape` et `categorie_slug` ; tant que ce SQL n'est pas exécuté, les photos sont enregistrées (liste, ZIP, PDF) mais ne réapparaissent pas dans les étapes de la fiche après rechargement :
  `alter table fiches_chantier_photos add column if not exists etape text default ''; alter table fiches_chantier_photos add column if not exists categorie_slug text;`
- **Puissance** (fiches atelier) : la valeur reste en texte libre ; l'unité se choisit dans une liste — kW par défaut, W, CV, HP, kVA — et s'affiche telle quelle dans l'aperçu, le PDF, le Word et la couverture du rapport. Une fiche sans unité enregistrée reste en kW. L'unité est rangée dans `<champ>__unite` (ex. `puissance__unite`). La fiche chantier garde son champ « Puissance (kW) » inchangé.

## 6. Fiche Chantier

- Couleur : vert pétrole (constante `COULEUR_CHANTIER`), validée « pour le moment ».
- Liste en dossiers **client > N° DE > lieu** ; actions Ouvrir / Aperçu / Dupliquer / ZIP + PDF / photos / suppression ; même aperçu, PDF et ZIP que l'atelier.
- Statut : seulement Récupéré / En attente. Pas de statut « En cours » affiché, pas de lien avec le Planning.
- Le « lieu » = « Matériel / Identification lieux » (`ch_eq_nom`), premier champ de l'étape Équipement.
- N° de chantier = N° DE, un seul champ, rangé à côté du Client.
- 4 étapes : Informations générales → Identification équipement (se termine par la case « Entretien en atelier » pour Pompe / Moteur / Moto-réducteur) → Matériel → Manutention & Observations.
- Étape Matériel : lignes catégorie · désignation × quantité avec 3 états : **À renouveler**, **À commander**, **Utilisé, à ne pas renouveler**. Même sélecteur de catégories que l'assistant « Matériel à commander » (`ChoixMateriel`) + scan d'étiquette QR.
- À l'enregistrement, les lignes « à renouveler » et « à commander » partent automatiquement dans l'onglet Matériel (`synchroniserMaterielChantier`, demande `ch-<id fiche>`, sans doublon, sans modifier une ligne déjà commandée, sans mail).
- Imprimé groupé par état.

## 6 bis. Rapport client (Word et PDF)

Modèle de référence : le rapport « DE7591 Rapport d'entretien » de PMV (7 pages). Le contenu est construit une seule fois (`src/rapportModele.js`) puis mis en page en Word (`src/rapportDocx.js`) et en aperçu / PDF (`src/pdfUtils.js`) : les deux versions disent toujours la même chose. Toute évolution du contenu se fait dans `rapportModele.js`.

- **Structure** : page de garde (logo, « Rapport d'entretien », matériel, n° de série, client — DE, mois/année en grand sur une bande décorative) → page d'identification (coordonnées PMV, tableau client / référence / adresse / contact / localisation / n° et date de commande achat / bordereau / date de réception / départ de nos ateliers / descriptif des travaux, sommaire) → chapitres numérotés dans l'ordre du modèle : 1 Norme ISO et identification (tableau ISO, photo et description de la plaque), 2 Mesures avant entretien (photo à l'arrivée, essai mécanique avant démontage côté commande / côté opposé, mesures, consommation à vide), 3 Photo et observation au démontage, 4 Mesure des parties mécaniques (portées avec verdict, roulements installés), 5 Rapport électrique du bobinage (« après nettoyage / étuvage » selon la fiche ; valeurs U/V, V/W, W/U, masse, DAR ; captures d'appareil une par page), 6 Mesures après entretien (essai mécanique, mesure électrique à vide et en charge), 7 Conclusion (verdicts, photo après entretien, départ de nos ateliers, certifié par / réalisé par, liste du matériel de contrôle).
- **Mise en page sans trou inutile** : les chapitres s'écoulent à la suite les uns des autres (l'aperçu n'a plus une « feuille » par chapitre ; le PDF et le Word non plus) ; seules la page de garde et la page d'identification / sommaire ont leur propre page, et une capture d'appareil ne force plus de saut de page. Une photo, une paire de photos ou une capture qui ne tient pas dans le bas d'une page (non fractionnable) passe à la page suivante : un vide en bas de page reste donc possible dans ce seul cas.
- Un chapitre sans contenu n'est pas imprimé ; les cases « Sections à inclure » du formulaire restent respectées. Verdicts : « conforme » surligné en vert, « non conforme » en rouge, texte libre en gras.
- En-tête (logo, « Rapport d'entretien — DE — client ») et pied de page (« PMV Services, votre spécialiste de l'entretien du moteur électrique et annexe », « Page X sur Y ») sur toutes les pages sauf la couverture.
- Formulaire : champs ajoutés « N° / date commande achat », « Départ de nos ateliers (date) », « Départ de nos ateliers — contrôle final » (texte proposé : arbre protégé et serrage de la boîte à bornes vérifié), « Matériel de contrôle utilisé — dates de validité » (liste proposée, modifiable ; bouton pour la garder comme liste habituelle, stockée dans `parametres_app`, clé `rapport_materiel_controle`), « certifié par » / « réalisé par » à choix multiple (« CD et DN »). **Les dates de validité du matériel de contrôle sont à vérifier avant chaque envoi.**
- Photos allégées à l'export (1800 px, JPEG) : le Word passe d'environ 28 Mo à environ 2 Mo, le PDF de 76 Mo à environ 2 Mo ; l'orientation des photos de téléphone est corrigée.
- Test : en développement (`npm start`), `window.__rapportTest.genRapportDocx(v, data, photos)` et `window.__rapportTestHtml.genRapportHtmlLeger(...)` génèrent le rapport sans passer par l'interface ; le Word se contrôle en l'ouvrant dans Word, le PDF en l'imprimant depuis Edge.
- À savoir : l'onglet Rapport affichait « 0 fiche » tant que « Fiche Atelier » n'avait pas été ouvert ; la liste des fiches est maintenant chargée dès l'ouverture de l'appli.

## 6 ter. Calendriers (onglet « Calendrier »)

- But : noter à qui on a remis un calendrier annuel pour ne pas en redonner. Accessible aux deux rôles (technicien et administrateur).
- Table Supabase `calendriers` (SQL dans `SQL_CALENDRIER`, `src/Calendrier.js`, à coller une fois par le responsable ; tant qu'elle manque, l'onglet affiche l'écran d'activation) : édition (année du calendrier), date de remise, client, contact, nombre de grands, nombre de petits, noté par.
- « Donner un calendrier » : un client (liste des clients existante, ajout possible), puis un ou plusieurs contacts **du même client** (liste du carnet de contacts existante, ajout possible), avec le nombre de grands et de petits pour chacun ; date de remise (aujourd'hui par défaut) et édition (année suivante à partir de septembre). Les contacts déjà connus du client (remises précédentes, carnet rattaché à la société) sont proposés.
- Avertissements : le client ou le contact a déjà reçu un calendrier pour l'édition choisie (quantités et date affichées).
- **Compteur de stock** (en haut de la page, pour l'édition choisie) : grands et petits restants sur le stock de départ, avec barre (orange sous 20 %, rouge au-delà du stock). Stock de départ de l'édition en cours : **180 grands et 100 petits** ; modifiable par l'administrateur (« Stock de départ »), rangé dans `parametres_app` (clé `calendrier_stock_<édition>` = « grands,petits »). Une autre édition sans stock saisi affiche seulement les quantités données ; « Toutes » masque le compteur. Le formulaire annonce le stock restant après l'enregistrement et prévient si on dépasse le stock.
- Liste : barre de recherche (client, contact, date, mois, mots dans le désordre, sans accents), filtre par édition, regroupement par client avec totaux grands / petits, date et personne qui a noté, suppression d'une ligne avec confirmation.
- **Modifier une remise déjà notée** (bouton ✏ sur chaque ligne) : quantités de grands et de petits, contact, date de remise et édition ; au moins un calendrier doit rester (sinon on supprime la ligne). Le compteur de stock se met à jour tout seul.

## 6 quater. Suivi clients — relance devis, prospection, RDV, devis refusés (profil Commercial uniquement)

- Onglet « Suivi clients » à **quatre sous-onglets** : **Relance devis** (ouvert par défaut), **Prospection**, **RDV**, **Devis refusés**. Les trois premiers portent une pastille rouge (relances en retard / RDV d'aujourd'hui ou passés non clôturés). À l'ouverture, la page tombe sur le premier sous-onglet qui a une alerte (devis, puis RDV, puis prospection), sinon sur Relance devis.
- Tables Supabase `suivi_devis`, `suivi_prospects` et `suivi_rdv` : **un seul SQL à coller** (`SQL_SUIVI_CLIENTS` = `SQL_SUIVI_DEVIS` + `SQL_PROSPECTS` + `SQL_RDV`, `src/SuiviClients.js`, rejouable sans risque, met aussi à jour une base qui avait l'ancienne version : colonne `motif_refus`). Tant qu'une table manque (ou que la colonne `motif_refus` manque), le sous-onglet concerné affiche l'écran d'activation. Visible et chargé pour le Commercial ; chargé aussi pour l'administrateur (fiche client, lecture seule).

### Relance devis

- Une ligne = un devis : **N° de DE** (normalisé « DE1234 » ; si une fiche atelier ou chantier porte ce DE, son client est proposé), **client** (liste des clients existante, ajout possible), **contact** (carnet de contacts existant ; ajout d'une nouvelle personne avec son numéro et son mail ; téléphone et mail repris du carnet), objet, montant HT, date du devis, statut (À envoyer, Envoyé — en attente, Accepté, Refusé, Sans suite), commentaire, historique.
- **Relance** : soit une **date précise**, soit un **délai** (jours, semaines ou mois à partir de la date du devis, ex. 8 semaines), soit aucune. Quand la date est atteinte ou dépassée, la ligne passe en rouge (orange le jour même), l'onglet affiche une pastille avec le nombre de relances à faire et le tableau de bord du Commercial liste ces relances (visible aussi sur téléphone).
- « ✓ Relancé » : note facultative, la prochaine relance reprend le même délai (modifiable) ; chaque relance et chaque changement de statut est gardé dans l'historique de la ligne.
- Tableau interactif (à partir de 1000 px) ou cartes (téléphone, tablette portrait) : recherche, filtre par statut, tri (relance, client, date, montant), statut modifiable directement, appel téléphonique et mail de relance préremplis en un geste, export CSV de la liste affichée, indicateurs (à relancer, en attente avec montant total, acceptés avec taux de réponses positives, refusés).
- **Lien avec les fiches** : si une fiche atelier porte le même N° de DE, un lien « 📂 fiche atelier » l'ouvre (lecture seule) et le retour ramène au même sous-onglet ; le nom du client ouvre sa fiche client.
- Les devis **Refusé** et **Sans suite** ne figurent plus dans « Relance devis » (la tuile « Refusés » renvoie vers leur sous-onglet).

### Devis refusés

- Passer un devis en Refusé ou Sans suite (liste déroulante du statut) ouvre une fenêtre qui demande le **motif** (obligatoire : prix trop élevé, délai trop long, concurrent retenu, pas de budget / projet reporté, projet abandonné, plus de réponse, autre) et une précision facultative ; le tout va dans l'historique et la colonne `motif_refus`. Le formulaire d'un devis propose aussi le motif.
- Sous-onglet : liste (tableau ≥ 1000 px, cartes sinon), puces de filtre par motif avec effectifs, recherche, nombre de devis et montant refusé, « ↩ Remettre en suivi » (statut Envoyé, relance dans 4 semaines), modification, suppression.

### RDV

- Table `suivi_rdv` : date, heure, entreprise (client ou prospect, même champ que la prospection), contact (carnet), téléphone, mail, lieu (lien vers la carte), objet, statut (Prévu, Fait, Annulé), compte rendu.
- Tuiles : À venir (dont aujourd'hui), À clôturer (prévu mais date passée), Faits, Annulés ; « ✓ Fait » demande un compte rendu facultatif. Ouvert par défaut sur « À clôturer » s'il y en a. Un RDV d'aujourd'hui ou passé non clôturé compte dans la pastille de l'onglet.
- Le tableau de bord du Commercial liste les RDV d'aujourd'hui, de demain et à clôturer.

### Prospection

- Deux listes dans le même tableau (filtre par tuile ou par « Afficher ») : **À démarcher** (entreprises à aller voir : nom, secteur d'activité, potentiel de travail, contact facultatif) et **Démarchés** (entreprise déjà contactée : contact, téléphone, mail, date du démarchage, **relance par date ou par délai**, 4 semaines proposées). Boutons « ➕ À démarcher » et « ➕ Déjà démarché ».
- **Nom d'entreprise** : proposé à partir de la liste des clients existante ; un nom qui n'y figure pas porte l'étiquette **Prospect** (sinon « Client »). Un prospect n'est PAS ajouté à la liste des clients des fiches.
- Contact : carnet de contacts existant (ajout possible avec téléphone et mail) ; téléphone et mail repris du carnet. Secteur : suggestions tirées des secteurs déjà saisis.
- Statuts : À démarcher → **Démarché** (bouton « ✓ Démarché » : note + date ou délai de relance) → Devenu client / Pas intéressé. « ✓ Relancé » : note + prochaine relance (mêmes règles que les devis) ; tout est gardé dans l'historique. Repasser un prospect en « À démarcher » efface sa relance.
- Relance : même code couleur que les devis (rouge en retard, orange aujourd'hui, jaune sous 7 jours, vert au-delà) ; seuls les prospects « Démarché » sont suivis. Recherche, tri (relance, entreprise, secteur, dernier ajouté), export CSV, appel et mail de relance préremplis. Tableau à partir de 1000 px, cartes en dessous.

### Notifications du Commercial

- Dans l'appli : calculées à l'ouverture (et au chargement de la page) en comparant les dates à la date du jour ; aucune notification poussée, rien quand l'appli est fermée.
- Où elles apparaissent : pastille rouge sur l'onglet « Suivi clients » (devis + prospects en retard ou à faire aujourd'hui + RDV d'aujourd'hui ou passés), pastille sur chaque sous-onglet, blocs « Relances à faire » et « Rendez-vous » du tableau de bord (avec appel en un geste), lignes rouges ou orange dans les tableaux, bouton « prospects à démarcher ».
- **Résumé du matin par mail** (voir § 9) : relances de devis et de prospection en retard ou du jour, RDV d'aujourd'hui, de demain et passés à clôturer, relances des 7 prochains jours, nombre d'entreprises à démarcher.

## 6 quinquies. Clients (profils Commercial et Administrateur, lecture seule)

- Onglet « Clients » : liste de tous les clients (liste des clients des fiches + noms rencontrés dans devis, fiches, calendriers, prospection, RDV), recherche par nom ou N° de DE, filtre (tous / suivi en cours / prospects seulement), 60 par page ; étiquette Client ou Prospect ; dernière activité.

Aucune table de plus : `src/Clients.js` lit les données existantes. Le nom d'un client dans le suivi clients (devis, RDV, prospection) ouvre sa fiche.

## 6 sexies. PMV Rail — fiche « Cheminée de freinage », numéros DV et stock RAIL

Filiale PMV Rail (clients PATRY, EIFFAGE RAIL SAS, IMATEQ). Procédure reprise de « Procedure controle cheminées V2.xlsx » ; le rapport final d'exemple (DV0040) a servi à choisir ce que la fiche doit recueillir. **Le rapport client des cheminées est codé** (voir § 6 sexies bis) : bouton « 📧 Rapport client » sur la fiche et fiche présente dans la liste de l'onglet Rapport.

- **Numéros DV** (`src/railClients.js`, sans dépendance) : pour les clients du rail, le N° de chantier s'écrit « DV0000 » au lieu de « DE0000 » — fiche atelier (champ et libellé « N° DV »), fiche chantier, suivi clients, listes. La liste des clients est modifiable par l'administrateur (Stock → onglet RAIL → « Clients PMV Rail ») et rangée dans `parametres_app` (clé `clients_rail`) ; par défaut PATRY, EIFFAGE RAIL SAS, IMATEQ. Nom comparé sans accents ni majuscules (« Patry SA » reconnu). Des chiffres seuls reçoivent le préfixe du client ; un préfixe tapé (DE ou DV) est conservé ; si le N° est saisi avant le client, son préfixe suit le client. Les soldes du fichier « Client PMV Rail.xls » ne sont ni importés ni utilisés (noms seulement).
- **Fiche Cheminée de freinage** (`type_materiel` = « Cheminée de freinage », carte 🚆 de « Nouvelle fiche », champs dans `src/Cheminee.js` : `CHAMPS_CHEMINEE`, `ETAPES_CHEMINEE`). N° toujours en DV. Technicien à chaque étape (choix multiple habituel, coché d'office). L'en-tête et le dossier prennent « Cheminée <n° de cheminée> » comme lieu.
  - **Réception** : date, N° DV, client, **délai demandé** (comme les autres fiches : durée + unité, ou « Pas de délai demandé » dans la liste d'unités ; il alimente l'urgence du tableau de bord), **N° de cheminée** (bouton rond « ? » : « se lit sur la plaque jaune, ligne n° de série »), **SNCF ou IMATEQ** (choix libre pour chaque cheminée) avec message selon le choix, **N° de loco** (obligatoire si IMATEQ), « des plaques déjà gravées ? » (si oui : texte libre — lesquelles et quels numéros), enlèvement par nos soins, livraison transporteur, palette (schéma + photo + conforme oui/non + observation), 5 photos au déballage (globalité, plaque jaune, plaque moteur, plaque pressostat, plaque inox), identification de la résistance de freinage (type obligatoire, n°), du ventilateur (type obligatoire, n° de fabrication, débit, pression, puissance).

Les pièces à changer (roulements, joints) alimentent le « Matériel à commander » comme pour un moteur.
  - **Remontage cheminée** : intégrité des résistances ; **tableau des 8 résistances** (isolement 5 kV et 10 kV, résistance en Ω, casse en nombre, serrage, **conformité calculée**) ; photos des isolateurs cassés (obligatoires dès qu'une casse est saisie) ; plaque de mica, barrettes ; résistances partielles Rack 1 (N°1 à 4) et Rack 2 (N°5 à 8), globale ; isolements partiel et global 5 / 10 kV ; **conclusion calculée** ; **gravure des 8 plaques** (numéro de chaque plaque : obligatoire pour une cheminée SNCF, facultatif pour IMATEQ ; les plaques déjà gravées à l'arrivée sont rappelées) ; **isolateurs** (SNCF : n° de lot obligatoire, tous changés ; IMATEQ : nombre changé obligatoire, lot facultatif) ; serrage au couple, feutre ROUGE, **déflecteur** (remplacé / non remplacé / fourni par le client / manquant), vis contrôlées + technicien, photos état visuel, palettisation au départ, fermeture de la porte, « rapport rédigé » (facultatif), **bon de livraison, date de mise à disposition, site de livraison**, 2 techniciens de contrôle qualité.
  - **Conformité automatique** (`Cheminee.js`) : résistance d'un rack 0,8025 Ω ± 5 % (0,762 à 0,843 Ω) ; 4 résistances en série (partielles) 3,21 Ω ± 5 % (3,05 à 3,37 Ω) — normes du rapport DV0040 ; **isolement : 1 GΩ minimum** (le rapport ne donne pas de norme chiffrée ; constante `ISOLEMENT_MINI_OHM`, à confirmer). - **Page Maintenance** (`src/Maintenance.js`) : onglets *Fiches atelier* (un jeu par type de matériel), *Fiches chantier* (un jeu par type d'équipement), *Planning*, *Historique*. Pour un type et une étape : **ajouter** un champ (texte court ou long avec dictée, nombre + unité, liste de choix avec ou sans « Autre », oui/non, date, photo « au moins une », intertitre) à l'endroit voulu (« ＋ Ajouter dessous »), **renommer**, changer les choix d'une liste, une note, **obligatoire / facultatif**, **masquer / réafficher**, **déplacer** (▲ ▼), **retirer** un champ ajouté ; « Voir comme dans la fiche » affiche l'étape telle que les techniciens la verront. *Planning* : renommer, recolorer, réordonner et **ajouter** des colonnes (statuts). Les modifications se préparent en brouillon puis se **publient** d'un coup : définitives pour toutes les fiches, anciennes comprises ; l'historique garde 20 versions (« Revenir à cette version »).
- **Changer un champ d'étape** (demande du 20/10/2026, bouton **« ↪ Autre étape »** sur chaque champ, sauf dans l'étape « Entrée » qui ne reçoit ni ne perd de champ) : on choisit l'étape d'arrivée et la place (en tête, après tel champ, à la fin) ; les champs **affichés sur la même ligne** (même `groupe`, ex. diamètre nez de roue / volute) partent ensemble si la case est cochée. Le champ garde son identifiant et ses valeurs. Dans l'étape d'arrivée il porte « ↪ vient de « … » » avec **« ↩ Remettre dans « … » »** ; dans l'étape d'origine un bandeau liste ce qui en est parti (lien vers l'étape d'arrivée). Avertissement « ⚠ pas toujours présente » si l'étape d'arrivée n'apparaît pas dans tous les cas où l'étape d'origine apparaît (moteur neuf, ventilateur seul, étape « Suivi devis et commande ») : le champ ne serait alors pas demandé. Sur une fiche qui a déjà passé l'étape d'arrivée, le champ n'est plus demandé (valeurs conservées). Technique : `deplace[id]={apres, etape}` dans la configuration (`configFiches.js`) ; un champ posé après un champ lui-même déplacé attend que celui-ci soit en place ; ▲ ▼ gardent l'étape d'arrivée.
- **Fiche pompe (20/10/2026)** : **diamètre de nez de roue** et **diamètre de volute intérieur** sont maintenant en tête de l'étape « Mécanique pompe au démontage », juste sous « Pompe neuve » (ils étaient dans « Rotation avant démontage pompe ») ; mêmes identifiants, toujours obligatoires, demandés aussi pour une pompe neuve. Cette étape déclenche le passage automatique de la fiche en « Devis » (`ETAPE_DECLENCHE_DEVIS` dans `App.js`) : les deux mesures sont donc à saisir avant sa validation. **État visuel du flasque et de l’arbre** (demande du 20/10/2026, comme au démontage moteur) : dans cette même étape, après le roulement avant puis après le roulement arrière, « État visuel flasque avant / arbre avant pompe » et « … arrière pompe » (OK / Marqué, côte à côte, obligatoires, seulement si la pompe n’est pas neuve) ; identifiants `etat_flasque_av_p`, `etat_arbre_av_p`, `etat_flasque_ar_p`, `etat_arbre_ar_p` (distincts de ceux du moteur). Les mesures en mm du flasque et de l’arbre du moteur n’ont pas été reprises pour la pompe. **Roulements de la pompe : choix Oui / Non** (demande du 21/10/2026) : nouvelles questions obligatoires « Roulement avant pompe » et « Roulement arrière pompe » (`roulement_av_p_present`, `roulement_ar_p_present`, seulement si la pompe n’est pas neuve) ; avec **« Non »**, les champs de ce roulement disparaissent (type, état, « changé », et plus aucune pièce « Roulement … pompe » proposée à commander) ; sans réponse ils restent affichés (fiches déjà en cours). Les joints à lèvres et l’état visuel du flasque / de l’arbre restent demandés dans tous les cas.
- **Ce qui reste dans le code** (à demander) : les étapes elles-mêmes (ajout, ordre, suppression : les fiches en cours en dépendent), les règles « n'apparaît que si… » et les champs obligatoires sous conditions, les calculs et conformités automatiques, les schémas, et le **cœur des rapports client** (les rubriques écrites par le code ; mais on peut les masquer, les renommer et ajouter des blocs : § 10 ter).
- **Technique** (`src/configFiches.js`) : configuration JSON dans `parametres_app` (clés `config_fiches` et `config_fiches_historique`), posée **par-dessus** les définitions du code : `champsPourType` / `champsChantierPourType` renvoient `appliquerConfig(base, clé)` (clés « Moteur », « Pompe »… et « ch:Moteur »…), `appliquerStatuts` remplace sur place `STATUTS_CHANTIER` (le PDF lit `window.__statutsApp`). Sans configuration, les définitions du code sont renvoyées telles quelles. Relue au démarrage, au retour sur l'appli et toutes les 5 minutes ; copie locale `pmv_config_fiches`. **Ne jamais changer l'`id` d'un champ du code** : la configuration s'y réfère.
- **Voir la configuration** : `node scripts/lire-config.js` (lecture seule, ajouter `--json` pour la version brute) affiche ce que la Maintenance a changé (champs renommés, masqués, déplacés, facultatifs, ajoutés, colonnes du planning, dernière publication). **À lancer avant toute modification des champs ou du planning** (règle aussi dans `CLAUDE.md`).
- « Masquer » ne supprime jamais de données. Un champ photo ajouté se rattache à ses photos par son intitulé : le renommer coupe le lien avec les photos déjà prises.

## 10 ter. Rapports client modifiables par la Maintenance (onglet « 📄 Rapports »)

Demande du 20/10/2026 : pouvoir changer les rapports (moteur, pompe, ventilateur, cheminée…) **sans passer par le code** : placer un texte ou une ligne à un endroit du rapport et choisir **la case de la fiche atelier** à y reporter.

- **Où** : page Maintenance → onglet « 📄 Rapports » (profil Maintenance). Un jeu de réglages **par type de matériel** : Moteur, Moto-réducteur, Autre matériel, Pompe, Ventilateur, Cheminée de freinage. L'éditeur est `src/EditeurRapports.js`.
- **Plan du rapport** : la liste des rubriques du rapport actuel, dans l'ordre (`ANCRES_MOTEUR` dans `rapportModele.js`, `ANCRES_CHEMINEE` dans `rapportCheminee.js`, `ANCRES_GENERIQUE`). Pour chaque rubrique : **🚫 Masquer** (la rubrique et son contenu ne s'impriment plus ; un titre masqué emporte ce qui le suit jusqu'au titre de même niveau ou supérieur), **✏ Renommer** (titres) ou **✏ Modifier le texte** (textes fixes ; les champs {{…}} y sont permis), « ↩ Rétablir le texte d'origine ». Entre deux rubriques : **« ＋ Ajouter un bloc ici »**.
- **Blocs ajoutables** : *titre de rubrique* (chapitre numéroté pour les rapports « chapitres », titre pour la cheminée), *sous-titre*, *paragraphe* (une ligne saisie = un paragraphe), *lignes serrées* (une par ligne), *photo(s) de la fiche* (catégorie au choix, taille petite / moyenne / grande ; plusieurs photos de la même catégorie = côte à côte). Style : normal, gras ou **rouge**. Le bloc se place « juste avant » une rubrique (ou au début, ou à la fin) et se déplace avec ▲ ▼ ou en changeant la position. Pas de tableaux libres (les tableaux de la cheminée restent dans le code : masquables, pas redessinables).
- **Champs de la fiche** : menu « ＋ Insérer un champ de la fiche » = tous les champs de la fiche atelier du type, **y compris ceux ajoutés par la Maintenance** (leur libellé actuel). Écrits `{{identifiant}}` dans le texte. Mise en forme automatique : isolement « 119_GΩ » → « 119 GΩ », dates en jj/mm/aaaa, techniciens « CD et RC », « Autre: xxx » → « xxx » ; **l'unité d'un nombre n'est pas ajoutée** (on l'écrit dans le texte). « Ne pas imprimer la ligne si un de ses champs est vide » (coché d'office, ligne par ligne). Condition facultative : « Imprimer ce bloc seulement si [champ] est rempli / vide / égal à / différent de [valeur] » (ex. cheminée_origine égal à SNCF). Un champ interne (observations, « à recommander »…) est signalé ⚠ : le client verrait sa valeur.
- **Aperçu** : sous chaque bloc, « Résultat avec la fiche d'essai » (fiche réelle du même type au choix) ; bouton « 👁 Aperçu du rapport avec cette configuration » = le vrai rapport (PDF/HTML) avec le brouillon, **sans publier**.
- **Aperçu modifiable** (bouton « 👁 Aperçu modifiable », à côté de « 🗂 Plan ») : le rapport complet (sans la couverture) s'affiche dans la page avec la fiche d'essai ; en **survolant ou touchant** une rubrique, une barre propose **✏ Renommer** (ou **✏ Texte** pour un texte fixe), **🚫 Masquer**, **＋ Avant**, **＋ Après** ; un bloc ajouté (barre verte) se **modifie**, se déplace (▲ ▼) ou se retire (🗑). Le même formulaire que le plan s'ouvre à droite (sous l'aperçu sur téléphone) ; **l'aperçu se met à jour à chaque modification** (environ une demi-seconde ; seule la première génération est longue : les photos sont réduites une fois et gardées en mémoire) et garde sa position de défilement. Les textes calculés par le code (mesures, conformités, tableaux) ne se retapent pas dans l'aperçu : on les masque ou on place un bloc avant / après. « Après » = juste avant la rubrique suivante du plan. Les rubriques masquées sont listées sous l'aperçu avec « 👁 Réafficher ». **Réservé à la Maintenance** (décision du 20/10/2026 : tout changement de l'appli relève de la Maintenance). Technique : `src/apercuEdition.js` (génération avec cache d'images), `src/editionApercu.js` (style et script ajoutés au rapport en mode édition : blocs enveloppés dans `<div class="ed" data-ancre data-kind [data-bloc]>`, clics renvoyés par `postMessage`) ; n'existe ni dans l'aperçu normal, ni dans le PDF, ni dans le Word.
- **Tout le texte est modifiable (cheminée, demande du 20/10/2026)** : chaque morceau de texte du rapport cheminée (couverture, coordonnées de la société, pied de page, libellés des lignes d'identification, titres de page, phrases des chapitres, libellés des tableaux et des mesures, légende des couleurs…) passe par une **table de textes** `T(id, texte d'origine, variables)` (`creerTextes` dans `rapportPerso.js`) ; un texte modifié est rangé dans `textes[id]` de la configuration et remplace l'original. Dans l'aperçu modifiable, **✏ Textes** ouvre un champ par morceau de texte de l'élément survolé. Les **valeurs calculées** par le code s'écrivent `{nom}` (ex. `{date}`, `{nombre}`) : à garder pour qu'elles s'impriment ; les cases de la fiche s'écrivent `{{champ}}` et les réponses du formulaire du rapport `{{rapport:cle}}` (ex. `{{rapport:contact}}`). « ↩ Rétablir » remet le texte d'origine ; un texte identique à l'original n'est pas gardé. Le **plan** liste aussi la page de garde, les coordonnées et chaque ligne d'identification (Modifier le texte / Masquer). **Lignes d'identification** : type de bloc « Ligne d'identification (page de garde) » (libellé + valeur, à placer avant une ligne existante ou à la fin) ; ce qui reste dans le code = les valeurs calculées, la structure des tableaux et l'ordre des chapitres. Les identifiants des textes (`couv_titre`, `id.chantier`…) ne changent jamais. **Les rapports moteur / pompe / ventilateur gardent pour l'instant la modification des titres, des textes fixes et les blocs ajoutés ; la table de textes complète (phase 2) reste à faire pour eux.**
- **Ligne « Contact »** (page d'identification de la cheminée) : imprimée **juste sous « Dates d'entrée »**, avec le nom saisi dans le formulaire du rapport (champ « Contact (nom, affiché sous « Dates d'entrée ») » ; repris du champ `contact` de la fiche s'il existe) ; rien ne s'imprime si le nom est vide.
- **Enregistrer comme modèle de référence** (bouton qui remplace « Publier » dans cet onglet) : ce qui est enregistré devient le **modèle de tous les rapports de ce type** (aperçus, PDF, Word des prochains rapports) ; les rapports déjà envoyés ne changent pas. Brouillon → enregistrement, 20 versions gardées, « ↩ Revenir à cette version » : comme pour les fiches.
- **Brouillon → Publier**, 20 versions gardées, « ↩ Revenir à cette version » : comme pour les fiches. Sans réglage, les rapports sont **exactement ceux du code**. Les rapports déjà envoyés ne changent pas ; les prochains aperçus / exports utilisent la version publiée. Si la configuration ne peut pas être lue, le rapport se génère avec le code seul.
- **Pompe et ventilateur** (qui n'avaient pas de rapport) : couverture, identification du chantier (client, DE, référence, coordonnées du formulaire), conclusion (signatures, matériel de contrôle) automatiques ; **tout le reste se compose dans l'éditeur**. Le bouton « 📧 Rapport client » est maintenant sur toutes les fiches et tous les types figurent dans l'onglet Rapport (formulaire réduit pour pompe / ventilateur : coordonnées du chantier, signatures, matériel de contrôle).
- **Technique** : `src/configRapports.js` (config JSON dans `parametres_app`, clés `config_rapports` et `config_rapports_historique`, même principe que `configFiches.js`), `src/rapportPerso.js` (application au modèle du rapport : masques, textes, blocs, champs, conditions — module sans dépendance). Les pages de rapport transmettent `photos._meta = {type, fiche (photos), champs, config}` (jamais enregistré) aux constructeurs de rapport. **Ne jamais changer l'identifiant d'une rubrique** (`ANCRES_*`, ids des blocs du rapport) : la configuration s'y accroche ; une rubrique absente (vide, masquée) : le bloc se place avant la rubrique suivante qui existe, sinon à la fin. `node scripts/lire-config.js` affiche aussi les rapports personnalisés.

## 11. Technique à ne pas casser

- `src/App.js` utilise des fins de ligne CRLF ; modifier par script tenant compte des CRLF ou avec l'outil d'édition, jamais par remplacement global aveugle.
- Pagination Supabase pour toute table pouvant dépasser 1000 lignes.
- Paramètres de l'appli : table clé/valeur `parametres_app` (dont `clients_rail`, liste JSON des clients dont les numéros sont en DV).
- Table `rail_stock` (stock RAIL) : SQL dans `src/Rail.js` (`SQL_RAIL`), collé par l'utilisateur ; l'erreur `PGRST205` = table absente (bandeau d'activation).
- Les modifications de base (DDL) passent par un SQL que l'utilisateur colle lui-même ; l'appli affiche un bandeau d'activation tant que la table manque.
- Cache PWA : après un déploiement, prévoir un rechargement forcé côté appareil.
- Un déploiement Vercel peut échouer sans rapport avec le code : relancer avec un commit vide (`git commit --allow-empty`).
